# First captured JPEG can disagree with the completed viewport resize

Run `node docs/evidence/native97-public-first-frame-repro.mjs` from this checkout after installing the pinned dependencies and full Chromium. Exit zero means the diagnostic completed; inspect each returned JPEG size for capture acceptance.

The actual portable run used Playwright1.64.1, full Chromium156.0.8078.4, Node24.19.0 on Linux and the reviewed9f975 browser core. Seven of eight fresh pages returned a short first JPEG despite a requested/logical viewport of320×240. The script uses public APIs, parses the first received JPEG header, and closes pages/browser in `finally`. It does not skip frames, take screenshots, warm up rendering or modify protocol responses. [Exact source hash and results](native97-public-first-frame-proof.json) retain the observations. This is a local engine-boundary reproduction, not proof of the precise native macOS trigger.

A separate passive check observed five short first JPEGs in six cases even though `Page.frameResized` preceded viewport API completion and native screencast metadata reported deviceHeight240. [Metadata receipts](native97-first-frame-metadata-proof.json) show why those signals cannot establish image dimensions. An explicit real `Browser.setContentsSize` control produced the requested first size in only one of four cases; [all eight control/intervention cases](native97-contents-size-proof.json) are retained. None supports a reliable command-only fix.

Native96 separately captured320×98 input and independently decoded gray padding in frame zero despite a red source PNG. Native97's original macOS recording passes; that sample does not clear the earlier failure or the local mismatch above. Ordered viewport commands address a demonstrated scheduling race, but do not establish general first-frame readiness. The rejected146 hidden-window change, visible-size commands, encoding rewrite, frame discard and renderer warmup are not shipped as fixes. Reliable first-frame capture remains an open acceptance blocker.

The independent journal timing probe is a different investigation: [aggregate actual Codex/MCP/SQLite measurements](native97-journal-latency-proof.json) show no persistent Linux journal latency bottleneck in that sample. They do not diagnose the earlier Windows timeout or authorize timeout/SQLite-setting changes. No upstream issue or external message was sent.
